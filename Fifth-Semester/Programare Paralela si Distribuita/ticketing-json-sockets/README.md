# Ticketing (Client–Server) — JSON line-delimited over TCP sockets

## Overview

Java **client–server** system that manages concurrent **ticket pre-reservations, payments, expirations and refunds** for events happening in a single day.

Communication is implemented using **TCP sockets**, with **one JSON message per line** (JSON line-delimited protocol).

The system is designed to handle **high concurrency**, especially at ticket sale opening, and ensures **data consistency** through explicit synchronization mechanisms.

## Functionalities (mapped to requirements)

- **N events × M categories**, each category having:
  - price `P(i,j)`
  - initial stock `L(i,j)`

- **Pre-reservation (RESERVE_REQUEST)**:
  - checks availability
  - immediately decreases available stock
  - creates a `Rezervat` record with timestamp

- **Payment (PAY_REQUEST)**:
  - allowed only within `T_plata` seconds
  - updates reservation status to `Vandut`

- **Expiration handling**:
  - if payment does not occur within `T_plata`, reservation is cancelled
  - tickets are restored to stock

- **Refund (REFUND_REQUEST)**:
  - allowed only for `Vandut` reservations
  - restores stock
  - records a negative amount in refunds

- **Periodic checker (every 5s or 10s)**:
  - validates stock integrity (`sold + reserved ≤ initial`)
  - cleans expired reservations
  - computes balance per event (`Plati − Rambursari`)
  - appends snapshot to text file:
    - timestamp
    - event, category, remaining stock
    - unpaid and expired reservations

- **Graceful shutdown**:
  - server shuts down after a configurable time
  - notifies all connected clients via `SERVER_SHUTDOWN`

## Concurrency and Synchronization

- The server processes client requests using a **fixed thread pool** of size `P`.
- **Each reservation request is processed asynchronously using a Future** on the server.
- Clients use **CompletableFuture per request**, correlated by `requestId`.

### Synchronization strategy

- **Per (event, category) lock** → protects stock updates
- **ReadWriteLock (checker vs refund)**:
  - periodic checker → `readLock`
  - refund (complex transaction) → `writeLock`

This guarantees:
- checker does **not** run during refunds
- checker **can** run between reservation and payment

## Requirements

- Java 17+
- Gradle 8+

## Project Structure

- `com.ticketing.server.*` — server, business logic, synchronization
- `com.ticketing.client.*` — interactive CLI client
- `com.ticketing.sim.*` — automated 4-client simulation
- `data/` — generated runtime logs and snapshots
- `runs/` — results from scripted executions (5s / 10s)

## How to Run the Server (manual)

From project root:
```
gradle runServer --args="--port=5050 --threads=8 --tPlataSec=5 --checkIntervalSec=5 --shutdownAfterSec=180"
```

Parameters:
- `--port` — TCP port (default 5050)
- `--threads` — number of server threads `P`
- `--tPlataSec` — payment timeout `T_plata`
- `--checkIntervalSec` — checker interval (5 or 10 seconds)
- `--shutdownAfterSec` — server lifetime (default 180s = 3 minutes)
- `--dataDir` — output directory (default `data`)

## How to Run the 4-Client Simulation

In another terminal:
```
gradle runSimulator --args="--host=127.0.0.1 --port=5050 --clients=4 --reserveEverySec=2"
```

The simulator:
- spawns **4 clients**
- sends **one reservation every 2 seconds per client**
- randomly chooses **event, category and quantity**
- pays with **random delay** (sometimes > `T_plata` to force expirations)
- occasionally triggers **refunds**
- stops automatically when the server sends `SERVER_SHUTDOWN`

## Automated Script 

To generate **both required runs (5s and 10s)** automatically:

The script:
1. Starts the server
2. Waits briefly for initialization
3. Starts the simulator
4. Waits for automatic server shutdown
5. Saves all outputs in **separate folders**

## Performance Evaluation

Measurements collected during full server runs (≈3 minutes).

### Checker interval = 5 seconds

```
RESERVE | throughput=0.65 req/s | avg=12.07 ms | p95=3.24 ms
PAY     | throughput=0.49 req/s | avg=2.20 ms  | p95=3.36 ms
REFUND  | throughput=0.03 req/s | avg=1.58 ms  | p95=2.04 ms
```

### Checker interval = 10 seconds

```
RESERVE | throughput=0.75 req/s | avg=13.33 ms | p95=3.32 ms
PAY     | throughput=0.52 req/s | avg=2.36 ms  | p95=3.35 ms
REFUND  | throughput=0.02 req/s | avg=1.45 ms  | p95=1.99 ms
```

### Observations

- Larger checker interval slightly improves throughput by reducing contention.
- Reservation latency remains stable under concurrent load.
- Refunds correctly block the checker as required.
- Throughput is mainly limited by the client generation rate (4 clients × 2 seconds).
